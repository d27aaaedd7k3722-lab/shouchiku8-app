# 引き継ぎ — 工場見積 PDF から NEO を作る仕事

別のセッション・別の担当者が、この一式を初めて触るときに最初に読む文書。
**最終更新: 2026-09-12**（実機コグニでの検証と Codex 監査を反映）

---

## 1. 何をする仕事か

自動車の修理工場から届いた**見積書 PDF** を読み取り、損害保険会社に出す**見積ファイル `.neo`** を作る。
`.neo` は自動車損害査定ソフト「**コグニセブン**」（Audatex Auda7）が読み書きする形式で、
中身は独自圧縮のコンテナに SQLite が入っている。

**求められる品質は「人がコグニセブンに手入力して作ったのと見分けがつかないこと」**。
金額が合うだけでは足りない。行の並び、手入力の印、連動の扱いまで実機と同じである必要がある。
コグニは**ファイルを開いて画面を切り替えた時点で中身を作り直す**ので、
「ファイルの中では合っているのに、コグニで開くと変わる」書き方をすると事故になる（§5 を必ず読む）。

## 3. 絶対に守ること

1. **合計を合わせるために明細の金額・指数を動かさない**。
   工場が出した数字がすべて。調整してよいのは「塗装の材料代」だけで、それも工場見積に材料代の内訳が無いときに限る。
   例外は損害保険会社が協定で「この行の指数をこうする」と指定したときだけ
2. **合計が合わないまま「できました」と言わない**。差額の原因が説明できないなら未完了として報告する
3. **工場の指数がコグニの標準値と違っても、工場の値をそのまま残す**（手入力の印を付けて保持する）
4. **顧客情報を外へ出さない**。検証物は必ずリポジトリ外の `%USERPROFILE%\Documents\NEO_check\<案件名>\` に置く。
   `*.neo` と `NEO_check` は git に入れない。Codex など外部サービスに送るプロンプトに顧客情報を含めない
5. **既存の NEO や案件フォルダのファイルを上書き・削除しない**。
   コグニ実機で確認するときも、すでに開かれている窓は触らない・閉じない

## 4. 作業の流れ（要約）

詳細は `SKILL.md`。1 コマンドで通す場合:

```
python .claude\skills\pdf-to-neo\scripts\make_neo.py "$env:USERPROFILE\Documents\NEO_check\<案件>" --name "<顧客>_<車名>"
```

（**PowerShell の書き方**。この環境の既定シェルは PowerShell で、`%USERPROFILE%` は展開されずに
そのまま Python へ渡り「フォルダが無い」で止まる。bash なら `$USERPROFILE`、
cmd なら `%USERPROFILE%`。迷ったら**絶対パスをそのまま書く**のが確実）

| 段 | すること | 見る文書 |
|---|---|---|
| 1 | 入力（工場見積 PDF・車検証）を揃える | SKILL.md §1 |
| 2 | PDF を読み、書式を分類する | format_catalog.md |
| 3 | ADDATA から車種を特定する | SKILL.md §3 |
| 4 | `reading.json` に**印字どおり**写す（判断はしない） | reading_schema.md |
| 5 | `make_neo.py` で 下書き → 突合せ → 生成 → 検算 | SKILL.md §5 |
| 6 | `_draft_notes` と ★ を判断規則で 1 つずつ解決し、検算が全部 OK になるまで繰り返す | judgment_rules.md |
| 7 | コグニ実機で開いて確認する（**この文書の §5-1 の理由で重要**） | checklist.md |
| 8 | 納品する | SKILL.md §8 |
| 9 | 日誌と判断規則に記録する | SKILL.md §9 |

**段 4 で判断をしないこと**が品質の鍵。ref の決定・左右分割・板金ランク・装備・塗装行の解釈・
費用の分類・レバーレートは、すべて段 5 のスクリプトが決める。人が先回りすると再現性が落ちる。

### 最初の 1 件を始めるには

1. **実行する場所**: リポジトリ root（`…\【自動集計システム※作成中】\files`）。
   スクリプトのパスはすべてここからの相対で書く
**フォルダが 2 つ出てくるので呼び分ける**:

- **元案件フォルダ**（共有ドライブ。入力が置いてある。この PC では
  `Z:\2026年\MM月\DD日\<損保>_<顧客>_<番号>_<車名>_<地域>\` の形。
  ドライブレターと構成は PC・担当者で違うので、分からなければパスを直接もらう）
- **作業フォルダ**（ローカル。自分で作る。`$env:USERPROFILE\Documents\NEO_check\<案件名>\`）

2. **作業フォルダを作る**: `$env:USERPROFILE\Documents\NEO_check\<案件名>\`。
   顧客情報を含むのでリポジトリの中には作らない。ここに `reading.json` を書き、
   生成物（`estimate.json` / `<name>.neo` / `report.md` / `inspect.json` / `reading_check.json`）もここに出る
3. **入力（工場見積 PDF・車検証）は元案件フォルダから探す**。Read ツールで開く（画像 PDF でも読める）。
   `pypdf` の文字層は FAX だと空なので当てにしない
4. **元案件フォルダに既存の NEO（立会で作ったもの）があれば必ず見る** —— 作業フォルダではなく

   （既存ファイルは**開くだけ**。上書き・削除は禁止）

## 5. 実機で確かめた事実（間違えると事故る）

**この節が引き継ぎの核心**。いずれも実機コグニまたは実機 NEO で裏を取ったもので、
推測ではない。日付は確認した日。

### 5-1. コグニは画面を開いた時点で中身を作り直す

塗装ページを開くと、コグニは**連動パネルを明細（ERParts）から作り直す**。
したがって明細に対応する部品が無い連動行は、**開いた瞬間に消える**。

**塗装パネル（PaintingPanel）の `AddedFrom` の決め方**（**塗装パネルを持つ**実機 NEO 18 本・塗装パネル 44 行で例外なし。内訳は連動 41 行・パネル追加 3 行）:

**`AddedFrom` と工賃印（`WageByManual`）は別々に決まる**。まず `AddedFrom`:

| 明細に**同じ部品コードかつ同じ修理方法**の行が | `AddedFrom` |
|---|---|
| ある | 0（W/S 連動） |
| 無い | 1（パネル追加） |

工賃印は**指数が標準どおりかどうか**が先に効く:

| 塗装パネルの指数 | `WageByManual` | `Manual` |
|---|---|---|
| 標準と違う（工場の独自指数） | **`#`**（`AddedFrom` が 0 でも 1 でも `#`） | 1 |
| 標準どおり・明細に対応行あり | `''` | 0 |
| 標準どおり・明細に対応行なし | `*` | 0 |

- **部品コードだけでなく修理方法（取替 / 修理 / 板金）まで一致**していること。実機 69 行で食い違い 0
- **指数が標準と違うこと（手入力）は `AddedFrom` と無関係**。
  手入力でも「明細にあれば `AddedFrom=0`」「無ければ 1」は変わらない（実装 `estimate_to_neo.py` の
  `'AddedFrom': 0 if (is_bankin or linked) else 1` と `'WageByManual': '#' if pnl_manual else …`）
- 実測（2026-09-11、W90 ハイエース TRH229・ボディ 20。明細の部品コードは 4800、塗装パネルは枝番の 4801）:

  | 4801 の書き方 | 塗装ページを開いた結果 | 塗装計 |
  |---|---|---|
  | `AddedFrom=1`・`*`（パネル追加） | 2 行とも残る | **176,560**（工場見積と一致） |
  | `AddedFrom=0`・`''`（連動） | **4801 が消え**、枚数 1 で再計算 | 142,610（33,950 不足） |

- 生成器はこの違反を `ValueError` で止める（`estimate_to_neo.py` の `_linked_ng`）

**同じ型の事故が他のテーブルでも起こりうる**。新しいテーブルに書き込む処理を足すときは、
「コグニがその画面を開いたとき、この行を作り直さないか」を必ず考える。

### 5-2. 標準値と違う値は「手入力」の印を付けないと戻される

**塗装パネル**（`PaintingPanel`）は `Manual=0` / `WageByManual=''` のままだと、
コグニが塗装ページ表示時に ADDATA の標準値へ再計算する（`Manual` 列があるのはこの表だけ）。
工場独自の指数は `Manual=1`・`WageByManual='#'` で保持する。

**明細**（`ERParts`）も同じ。`WageByManual=''` の行は装備条件から標準区分を選び直され、
標準に無い指数の行は `Time/Wage=-1` に消える。
指数の列が無い非コグニ書式の見積は、**reading.json に `"index_policy": "manual"`** と書いて
全指数を `#` にする（draft が estimate.json へ引き継ぐ）。

### 5-3. 「標準値」の欄には標準値を入れる

`PaintingPlan.BaseTimeStandard` / `BoothTimeStandard` / `BaseWageStandard*` には
**ADDATA の標準値**を入れる（見積値ではない）。見積値を標準として書くと、
工場が標準と違う加算基礎を出したときに「標準どおり」の顔をしてしまい、コグニの再計算で戻る。
塗装パネルの `Time`（見積値）と `TimeStandardNew/1/2/3`（標準値）と同じ流儀。

2026-09-12 にこれを直したところ、実機 NEO との総当たり比較で**差のある実験が 1/67 → 0/67 になった**。

### 5-4. 20.DB（塗装パネル）はボディごとに別の行・別のコードを持つ

- レコード 39 バイト。**6 バイト目 = ボディコード**（0 から数えると `[5]`。実装は `r[5]`。`ADDATA_REVERSE_LOOKUP_SPEC.md` のバイト表は 0 起点なので「| 5 |」と書いてある）。値は 0 = 全ボディ共通 / 10 / 20 …
- 同じパネルが**ボディ違いで別コード（枝番）**になる車がある（W90 ハイエース: 4800 / 4801）
- 面積（= 塗装指数）がボディで違うので、**必ず車のボディコードで選ぶ**
- ただし選んだ結果、明細の部品コードと塗装パネルのコードがずれる。そのパネルは §5-1 により
  「パネル追加」（`AddedFrom=1`・`*`）で書く
- **面積（＝塗装指数）が一意に決まらない組が実在する**（20.DB を持つ 1,204 車種を全走査。2026-09-12）:
  枝番でコードも面積も違う組が **20 組（13 車種）**、同じコードに面積の違う行がある組が **258 組**。
  後者のほうが多く、2026-09-12 まで黙って先頭が選ばれていた（例 C39 ﾌ-ﾄﾞ 0600 = 131 / 149 d㎡）。
  一意に決まらないときは**同じコードの先頭を採ったうえで `body_unresolved` に控え、`inspect_estimate` / `run_case` が ★ で知らせる**（止まらない）。
  ★ が出た行は**見積書に印字された dm² と必ず突き合わせる**。違っていれば `paint.panels[].index` に見積書の指数を書く

### 5-5. 費用欄の 1〜8 は既定行

コグニの費用画面は 1〜8 が既定行（全角の固定名）、9〜36 が自由記入（半角カナ）。
見積書の費用名は**印字どおり（全角なら全角）**に写す。半角カナで写すと既定行に載らない。
既定行に載るかは語による（漢字・英字のキーワードは載る／カナは ショートパーツ・アライメント・
エーミング・コーティング だけ）。載らなくても金額・合計は同じ。

### 5-6. その他

- **消費税は 10% 固定**（生成器の `TAX = 0.10`、`Setting.TaxRate=10`）。8% 案件は作れない
- 塗装パネル行は**部品コード昇順**で保存される
- 左右のある部品は**左右別行**にする（コグニ流。数量 2 でまとめない）
- 塗装行の `dm²` は**塗装面積**。20.DB の**パネル面積**とは別物
- 工賃の丸め単位は既定 10 円だが、**100 円で丸める工場がある**（`wage_round`）

## 6. 検証の回し方

```

```

**全部が次の状態でなければ合格ではない**（2026-09-12 時点の基準）:

| 検証 | 合格の基準 |
|---|---|
| 実機 NEO との総当たり | **差のある実験 0 / 67** |
| 全ファイル一致（そのまま保存した実機 NEO） | **25 / 25 本** |
| 案件回帰 | **案件 7 / 不合格 0** |
| 単体テスト（生成器・スキル） | `*** FAILED` の行が 1 つも出ない |
| 終了コード | 最終行が **`=== verify_all exit 0`** |

**合格の判定は「最終行が `exit 0`」と「`*** FAILED` が無いこと」で見る。**
個々のテストの合格文言はまちまちで（`all ok` のものもあれば、`cells …` `FBANPA unit …`
`std: …` `known exceptions …` のように固有の数値行を出すものもある）、`all ok` だけを探すと
通っているテストを見落とす。

- 実機 NEO と個人情報を含む検証物は `%USERPROFILE%\Documents\NEO_check\` にある（配布物には入らない）
- 配布先の PC では `python .claude/skills/pdf-to-neo/scripts/env_check.py --self-test`
- **コード変更は Codex レビュー（`codex-loop` スキル、gpt-5.5 / reasoning effort xhigh）を通す**のが標準。
  Codex の指摘は鵜呑みにせず、**実データ（実機 NEO・案件）で裏を取ってから採用**する
  （実際、Codex の指摘のうち何件かは実データで否定されている）。
  **Codex には利用上限があり、使えない期間がある**（2026-09-12 に上限到達、復帰は 09-15）。
  そのときは `claude_neo_pipeline/tests/verify_all.sh` と、次の「文書を機械で見張る」仕組みで代える

| もの | 場所・備考 |
