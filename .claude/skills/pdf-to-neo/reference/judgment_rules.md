# 判断規則（estimate.json を書くときに人/Claude が決めること）

生成器が自動で決めることは書かない。ここにあるのは「セッションごとにぶれうる判断」を固定した規則。根拠はコグニ実機での確認結果（NEO_FILE_SPEC_COMPLETE.md / ADDATA_REVERSE_LOOKUP_SPEC.md）と実案件。

## 1. ref（部品コード）の選び方

1. **品番一致が最優先**。生成器の `find_ref` は品番 → 部品コード → 名称近似の順。品番が複数 ref に当たるときは「左右」「数量」「部位ブロック（直前行の ref のブロック）」で選ぶ
2. 品番の無い行（脱着・板金・修理）は **同ブロックの 12.DB 名称一覧** から選んで `code` を明示する。名称近似（`名称近似(0.8x)`）で決まった行は必ず目で確認する（例: 「右フェンダーライナー」は `Fﾌｪﾝﾀﾞﾗｲﾅﾘﾃｰﾅ`(172) ではなく `RFﾌｴﾝﾀﾞｽﾌﾟﾗﾂｼﾕｼ-ﾙﾄﾞ`(1002)）
3. 同じ品番が複数ブロックにある小物（バンパピース `52161-16010`、クリップ `90467-07214`、リテーナ）は **見積書のブロック見出しに従う**。右フェンダブロックの中のバンパピースは 1179/1183（RFバンパピース）、フロントバンパブロックなら 171
4. ADDATA に無い品目（ステッカー、社外品、輸入車部品、「ショートパーツ」的な明細）は `manual: true` で名称・金額をそのまま
5. トヨタ純正の色付き品番（`-A0`, `-C0`, `-A5`）は末尾込みで書く。13.DB の色別行と一致すれば標準品番になる。`(ﾄｿｳｽﾞﾐ)`（塗装済み）と `(ﾐﾄｿｳ)`（未塗装）は別行なので価格で区別する

## 2. 左右と数量

- コグニは左右を別 ref（別行）で持つ。見積書が「ウルトラソニックセンサ ×2」のように 1 行にまとめていても、**左 1 行＋右 1 行に分ける**。draft が自動で分けるのは **工賃も指数も無い行だけ**（工賃/指数のある行は `_draft_notes` に「左右分割せず」と出るので、reading で 2 行に割る）（合計は変わらない、コグニで開いたとき自然）
- 両側で n 個ずつのクリップ類は「左 ref ×n、右 ref ×n」の 2 行
- 片側にしか無い部品（フロントバンパピース ×3 等）は数量そのまま

## 3. 修理方法（DisposalCode）

| 見積書の語 | method | 備考 |
|---|---|---|
| 取替・交換・部品 | 取替 | 日産系の「部品」も取替 |
| 脱着・脱付 | 脱着 | 標準指数が無い部品（フェンダライナ等）は `#` になる。それで正しい |
| 修理・修正 | 修理 | 塗装パネルは PaintingPanel に連動 |
| 板金・鈑金 | 板金 | `bankin` を付ける（下記） |
| 脱着修理・脱着板金 | 脱着修理 | 連動加算あり |
| 調整・点検調整 | 点検調整 | 標準指数なし・部品代なし |
| 分解調整・O/H | 分解調整 | 11.DB に 'OH' 行がある部品だけ標準あり |

## 4. 指数と工賃（`#` と標準の関係）

- 見積書の指数が **コグニ標準と一致** → 標準行（`WageByManual=''`）。一致しない → `#`（手入力指数、TimeStandard には標準値が残る）。生成器が自動判定するので、estimate.json には見積書の指数をそのまま書く
- 工場の指数がコグニより低い/高いのは珍しくない（アルファード: Fバンパカバー 1.5 vs 1.9、グリル 0.8 vs 0.9）。**直さない**。工場の見積を再現するのが目的
- 工賃欄が空の付属部品は `wage: 0`。工賃欄自体が無い書式で取替/脱着行は `wage` 省略（標準で補完）
- 非コグニ書式で全行手入力にしたいときだけ `index_policy: manual`
- **工賃の丸め単位**: 工場のコグニ設定が 100 円丸めだと 0.25h×11,000 = 2,800 のように印字される。`wage_round: 100`（draft_estimate が自動推定）にすると生成器も 100 円丸めで標準行にする。10 円丸めのままだと `*`（手入力工賃）になり合計は同じでも標準行でなくなる（オデッセイ 2026-09-07）
- **工賃だけ手入力の行（`*`）は指数欄が空**: 工賃はあるが指数の無い行（板金 27,500 等）は Time −1 で書く（コグニ印刷も空欄。実 NEO 12051345 の 3800 も Time −1）。標準欄（TimeStandard/WageStandard）は残す
- **金額の手入力印 `*`（PartsPriceByManual）**: 部品金額が ADDATA の標準価格と違う行だけでなく、標準価格の無い行（手入力行・ADDATA に価格の無い品番・ディーラーオプション 08R04 バイザ等）に金額を入れた行も `*`（他工場 NEO 23 行、コグニ印刷 2026-09-07）。印字の「*#」は 金額 `*` ＋ 指数 `#` の 2 印
- 同じ部品コードを 脱着 と 板金 の 2 行で持てる（コグニ印刷 2700 スライドドア）。「同一コードの重複入力拒否」は同一修理方法のときだけ

### 4-2. 手入力の印と標準欄（コグニ実機 2026-09-08 で確定。NEO 仕様 §10-8）

- `*`（工賃だけ手入力）: 指数欄は空欄（Time −1）だが、標準指数・標準工賃・WorkCode は残る。生成器が自動で書く
- `#`（指数を手入力）: 指数は手入力値、標準指数・標準工賃は残る
- 部品価格の手入力 `*`: 印刷では工賃欄の右端に印が出る（価格欄には出ない）。価格の印か工賃の印かは、工賃欄が空欄で `*` だけあるなら価格の印
- **部品コードの無い手入力行**は reading で `M` を付け、修理方法欄が空欄なら method を空のまま（`|塗装費用||||1|61900||M*|`）。draft は method を `''` にし、生成器が `DisposalCode -1` で書く。修理方法が印字されていれば（取替 等）そのまま写す

## 5. 板金ランク

- 見積書の `(5dm²)` と指数から BANKIN.DB（面積 1〜40 d㎡ × A/B/C）を逆引きする。`inspect_estimate.py` が提案する（5 d㎡: A 1.1 / B 1.5 / C 2.1）
- `bankin.yes`: A=[1,1,1]、B=[1,0,0]、C=[0,0,0]（コグニ板金ダイアログの YES 3 つ）
- どのランクとも一致しない指数は `#` 手入力（`bankin` を付けず `index`/`wage` だけ）
- 面積が書かれていない板金行は `bankin` を付けず `index`/`wage` だけ（DamageRank 既定値は生成器が決める）

## 6. 装備（hints.eva_codes）

- 11.DB/13.DB の条件付き行は `flags[0:5]` = グレード、`flags[5:7]` = 装備レター（10.DB の A〜Z）。見積書の品番がどの条件行に一致するかで装備が分かる（`inspect_estimate.py` の「装備の提案」）
- 採用規則:
  1. 品番が **その装備の行にしか無い** とき採用（アルファード: ヘッドランプ 81145-V2230 → K 3眼LED、Fバンパカバー 52119-58988 → N）
  2. 10.DB の名称が車の実態と矛盾しないか確認（N=プレミアムサウンドが Fバンパの条件になっている例があるが、コグニのデータがそう定義しているので採用してよい。`hints.note` に根拠を書く）
  3. 標準指数が変わる装備（V インテリジェントパーキングアシスト2 で Fバンパ 1.9 → 2.0 等）は、見積書の指数がどちらに合うかも材料にする
  4. 迷ったら **付けない**（付けると標準品番・標準指数が変わり、`#` の行が増減する）
  5. draft が品番から自動採用した装備を外したいときは reading の `hints.eva_exclude`（例 `{"eva_exclude": ["T"]}`）。option_audit の「除外」提案はこれで実行する。
     **4WD の `Z`（車種特定が 4WD なら自動で付く）も `eva_exclude` で外せる**（2026-09-12〜）。
     逆に、**`eva_exclude` に入っているレターは `eva_codes` に足しても効かない**（除外が勝つ）ので、採用に転じるときは eva_exclude から消す
- 4WD の Z は resolver が自動付与。トリムコードは `vehicle.trim_code`

### 6-2. 装備が変えるもの（コグニ実機 2026-09-08、N-BOX J87 で 9 条件を保存して確認）

- 変わるのは **11.DB の変種（品番・価格）** と **15.DB の指数** の 2 つ。「装備が無いと計上できない部品」は 11.DB には無い（J87 / J22 / W82）
- 生成器の品番・価格の選択はコグニの再検索と全件一致。指数も一致するが 1 規則だけ追加した（**枠の取り合い**: 同じ枠のリンク符号を装備条件付きで持つ別部品がある車では、無条件の部品の標準指数が消える。例 U ディスチャージ車の 0400 ヘッドライト）。`option_audit.py` の ★ は「品番が別の装備の標準品番と一致する」検出、指数側はこの規則で生成器が自動処理
- 見積書に装備の注記（「インテリジェントクリアランスソナー付」等）があるか、品番が装備付きの標準品番と一致するときだけ `hints.eva_codes` に入れる。合計だけで装備の正否は分からない（合計は同じで品番・指数だけ変わる）

### 6-3. 品番の無い行の名称照合（別名辞書、2026-09-08）

- コグニに部品名の別名テーブルは無い。代わりに 12.DB の 4 桁部品コードがメーカー・車種をまたいで同じ部品を指すので、全車種の 12.DB を集計した `reference/part_code_names.json`（部品名 → 部品コード、23,000 名称）を辞書に使う。`scripts/build_part_names.py` で作る（1〜2 分。ADDATA 更新後に作り直す）
- draft は、品番も部品コードも無い行で、名称近似の類似度が 0.9 未満なら辞書のコード（この車種の 12.DB にあるもの・左右・部位ブロック優先）を採る。`_draft_notes` に「別名辞書(...)」と出る。違っていれば reading の `code` で指定

### 6-4. 連動・吸収（コグニ実機 2026-09-08 H1〜H7、NEO 仕様 §10-11）

- 生成器が自動で行う。reading では **見積書の行をそのまま**書けばよい（バンパビーム脱着があるとバンパ取替の指数が 0.8 → 0.9 になる、ドア取替があるとドアガラス脱着・ミラー取替の指数が消える、フェンダ取替があるとドア取替が +0.1、など）
- 見積書の指数が生成器の組合せ標準と違うときは `#` になる。連動・吸収の分だけ違う行は `report.md` の「手入力の行」に「← 連動・吸収込みの組合せ標準と差」「← 相手部品の作業に吸収される行」と出る（生成器が行に `_std_note` を付け、make_neo が表示する）。それ以外の `#` で標準と違う行は reading の修理方法（脱着 / 取替）や相手部品の有無を疑う
- WorkCode は 11.DB の区分文字列そのまま（0800 'TN1'）。指数の無い行にも付く。連動で足した区分は WorkCode に出ない。板金・修理行は空欄
- **見積の指数が生成器の組合せ標準と違えば '#' になる**（reading はそのまま）。工場のコグニは入力順に計算するので、相手部品を後から入れた見積では連動分が入っていないことがある（C06 ドア 2.0 vs 標準 2.3）。それでよい。'#' なら亮平さんがコグニで再検索しても見積値が守られる
- 塗装の塗膜は見積書の印字（塗装条件）を優先する。カラーコードの塗膜と違っても reading に印字どおり書く

## 7. 塗装

- パネル: 20.DB のコード（外板パネルの ref と同じ 4 桁）。`ratio` は見積書の 1/1・1/2・1/3。指数は見積書の値を書く。標準と一致すれば標準行、違えば Manual/`#`
- 塗膜・高機能: 見積書の見出しどおり。3コートパール（coat 4）は 2コートパール（3）と加算基礎が違う（アルファード 4.1 vs 3.4）ので読み間違えない
- 加算基礎数値（base）: 見積書の値。標準（T_KEI_3）と一致するのが普通。違うときは `index` を書けば手入力になる
- バンパ: 「フロントバンパー 取替」= 新品、「修正」= 変形修正/外傷修正（小/大は指数で判別）。一色/二色は見積書の記載か指数（23.DB の列）で決める
- ブース: 見積書に「ブース」行があるときだけ `paint.booth`（7-2）。無ければ書かない（既定はブース使用オフ）
- 材料代: `material_rate` は逆算（材料計 ÷ 塗装工賃計）。工場が行ごと四捨五入で合計が一括計算と違うときは `material` に見積値を入れる（コグニ側は `*` 手入力で保持。アルファード 41,141 vs 41,140）
- 塗装明細が無い見積は `total` 一括のみ。付加塗装（ワックス・ストライプ・低隠蔽性・2コートソリッド・2トーン）は README のキーで

### 7-2. 実機で確定した塗装の既定（2026-09-08、NEO 仕様 §10-9）

- ブース加算は見積書に「ブース」行があるときだけ `paint.booth` に書く。無ければ書かない（コグニの既定はブース使用オフ）
- 材料代は「割合」（`material_rate`、塗装工賃計 × % を一括四捨五入）か「手入力」（`material` に額）のどちらか。見積書の材料代計 ÷ 塗装工賃計 が 5% 刻みなら割合、そうでなければ手入力（`*`）
- バンパは 新品 / 変形修正 / 外傷修正小 / 外傷修正大 のいずれかを name に含める。新品は絞模様なし

## 8. 費用の分類

- `kind` は **見積書のどの合計に入っているか** で決める。「部品計」に入っていれば parts、「作業計」「諸費用計」「工賃計」なら wage
- 例（工場 B）: ショートパーツ 3,000・写真代 800 は部品計に含まれる → parts。コーティング 15,000 は諸費用計 → wage
- 例（工場 A（案件 C01））: 内張り費用・配線配管・アライメント・コーティング・産廃・光軸・エーミング → wage、ショートパーツ・車高調・ホイールバランス → parts
- 非課税（「非課税」明記）は `taxfree: true`

## 9. 顧客・保険

- 車検証から: 使用者名（customer.name）、使用者住所（address）、登録番号（reg_no）、有効期間満了日（term_date）、所有者（owner）
- 見積書から: 走行距離（kilometer）、見積日（est_date）
- 案件フォルダ名から: 損保会社（insurance.company）
- 分からない項目（郵便番号・証券番号・事故日・立会日・契約者）は **空文字**。推測で埋めない（フォルダの日付は事故日とは限らない）

## 10. 合計の扱い

- `totals` は見積書の合計欄をそのまま。検算は生成器が「費用込み/塗装込み」の組合せで一致判定する
- 合計が合わない原因の順番: (1) 数量×単価の読み違い (2) 費用の kind (3) 行の見落とし (4) 材料代の丸め
  (5) 工場側の円未満計上・10 円丸め（書式を問わず、`tax_round` でも説明できないときだけ 10-5 の 3 点セット）
- 消費税の計算単位は 10-3 の `tax_round`（draft が合計欄から自動判定。切り捨て/切り上げの工場設定を生成器も同じ単位で書く）。これで説明できる差に `tolerance` を使わない。**`tax_round` でも説明できない工場側の丸め**だけが 10-5 の 3 点セットの対象

### 10-2. 「合計を指定額に合わせる」依頼（協定額の NEO。N-BOX 2026-09-07）

亮平さんから「工場見積ベースで ○○円の NEO」「レバーレート X 円で、端数は塗装材料代で調整」と頼まれたとき:

1. 部品は工場見積の品番・金額をそのまま（部品計は動かさない）
2. 明細の工賃は工場の指数 × 指定レート（reading の `labor_rate` に指定レート、行は index だけ書く → script が丸めて工賃化）
3. 塗装は自社の初期見積（コグニ印刷）の構成を流用し、指定レートで指数×レート。塗料/塗膜は初期見積に合わせるとパネル・加算基礎がコグニ標準になる
4. reading に `target_total`（税込）を書くだけでよい。draft が材料代 1 円で試算して課税小計を実測し、差額を `paint.material` に入れ、`totals` も計算結果で上書きする（手計算は不要）。`paint.panels` が無い見積、工賃も指数も無い取替・脱着・脱着修理行がある見積では調整しない（`_draft_notes` に理由が出る）
5. reading の `totals` は印字どおりでよい（`target_total` があるとき draft の計算値で置き換わる）。検算が全部 OK なら目標どおり
6. 工場の指数がコグニ標準と違う行は `#` のまま（工場値を尊重）。工場側の左右表記が疑わしい行（損傷側と逆の R 等）は工場どおりに写し、報告で触れる

### 10-3. 工場コグニの設定（実機 2026-09-08 で確定）

- 工賃の丸め単位（1/10/100 円）は `wage_round`（draft が印字工賃から自動推定）。NEO では Setting.wb_Round だけが変わる
- 消費税の計算単位は `tax_round`（'切り捨て' / '切り上げ'。既定は四捨五入）。draft が合計欄から自動判定し、reading_check も WARN で示す。コグニ実機で確かめたとおり **1 円単位の 3 択しかない**（10-5）。`totals.neo_total` / `tolerance` / `tolerance_reason` で逃げるのは、この 2 つで説明できないとき（工場側の円未満計上・10 円丸め）だけ。そのときは make_neo を `--allow-neo-total` 付きで再実行する（無いと `neo_total` 一致でも不合格扱い）

## 10-4. 金額が税込で印字された見積書（ディーラー・二輪。2026-09-09 に 2 件連続）

- 「消費税10％対象(込) ¥…」「整備代金お見積金額（税込）」のように、**各行の金額まで税込**で刷る書式がある
  （二輪ディーラー（Ducati 系） / ディーラー BP センター（トヨタ系・案件 T1））。そのまま写すと課税小計が 1.1 倍になる
- **見分け方**: 税率を r（％）とすると、合計欄で「課税小計 × r% ≠ 消費税」なのに
  「課税小計 × r ÷ (100+r) = 消費税」が成り立つ（10% なら 課税小計 ÷ 1.1 × 10%）。
  `run_case.py` が合計不一致のときに ★ で指摘する。**10% 以外の見積は `totals.tax_rate` に税率を書く**
  （省略すると 10% として判定するので、8% の書式を見落とす）
- **`totals.tax_rate` が効くのはこの見分けだけ**。生成器の消費税計算は `TAX = 0.10` 固定で、
  NEO の `Setting.TaxRate` も 10 を書く（`estimate_to_neo.py`）。**8% など 10% 以外の税率の案件は現状つくれない**。
  そういう見積が来たら、税抜化までは同じ手順でできるが**消費税と合計が 10% で計算される**ので、
  NEO を納品せずに報告する
- **直し方**: 各行の部品金額・技術料に加え、**塗装行の工賃・材料代と `expenses[].amount`（費用）も** (100+r)/100 で割って
  税抜にする（10% なら 1.1、8% なら 1.08。r は `totals.tax_rate`）。生成器は estimate の金額を税抜として扱うので、
  費用を税込のまま残すと費用計・課税小計・消費税がずれる。`totals` は **`tax` / `total` と制御キー（`tax_rate` / `neo_total` / `tolerance` / `tolerance_reason`）以外の金額項目をすべて**税抜にする（`parts` / `wage` / `paint` / `paint_total` / `material` / `expense` / `expense_parts` / `expense_wage` / `frame` / `taxable` …。`run_case.py` はこれらを 1 つずつ突き合わせる）。`tax`（消費税額）と `total`（税込の御見積金額）は印字どおりの値をそのまま書く（生成器は税抜の積み上げに消費税を足して total と突き合わせる）。アクアの例: 部品 159,360 / 工賃 94,390 / 塗装 118,130 / 費用 18,000 / taxable 389,880 / tax 38,988 / total 428,868（印字は 175,296・253,572・428,868 の税込）
- **割り切れない行が出たとき**: 工場が行ごとに丸めて税込表示している書式なので、読み取りミスと決めつけない。
  (100+r)/100 で割った値を 1 円単位で四捨五入し、**合計欄の部品計・技術料計（税抜）と突き合わせて**確かめる
  （2026-09-09 の 2 件はどちらも税率 10% で全行が割り切れた: 1,914→1,740 / 8,976→8,160 など）。
  合計と合わないときは配分が違うので、工場に確認するか読み取りを見直す。行の金額を勝手に動かさない

## 10-5. 消費税の端数（コグニ実機 2026-09-09 で確認）

- コグニの設定は **その他 → 消費税設定**。「消費税を計算する / 税率 / 表示方法（外税・内税） /
  計算単位（四捨五入・切り捨て・切り上げ）」だけで、**計算単位は 1 円固定**。10 円・100 円は選べない
  （10円/100円があるのは総合計画面の「部品値引/割増計算単位」「工賃値引/割増計算単位」で、消費税とは別）
- 保存すると `Setting.tx_ArrangeFlag` が 1=四捨五入 / 2=切り捨て / 3=切り上げ になる（3 を実機で実測）。
  estimate.json の `tax_round` がこれに対応する
- **工場が消費税や合計を 10 円単位で丸める書式**（課税額計 506,010 に対し消費税 50,600 など）は、
  どの設定でも再現できない。`totals.neo_total`（コグニ計算の合計）と `totals.tolerance`、
  `totals.tolerance`（許容幅・円）、`totals.tolerance_reason` の 3 つを書いて差として許容する。
  理由を書かずに `neo_total` だけ置くと `run_case.py` が不合格にする
- **`tolerance` が効く項目は限定されている**（2026-09-12〜）:
  効く = 工賃計 / 塗装工賃計 / 塗装計(材料込) / 内板骨格 / 課税小計 / 消費税（工場の丸めで実際に差が出る項目）。
  効かない = **部品計・材料代・費用部品・費用工賃・費用計は 0 円一致**（工場が円単位で出すので丸めの差が出ない）。
  ここに差が出たら読み取りミスなので reading を直す。`tolerance` で許容した項目は ★ で知らせる
- **禁止**: 合計を合わせるために明細の金額を動かすこと（ショートパーツを 5,000 → 4,999 にする等）。
  協定案件で損保が指定した行の指数を動かすのは指示どおりの作業なので別（10-14）。
  工場の数字を書き換えることになるので絶対にしない（亮平さん指示 2026-09-09）

## 10-6. 指数の印字が無い工場書式（技術料だけの見積）

- 工場 R・ディーラー BP センター（トヨタ系）・Ducati のように **指数の列が無く技術料（円）だけ**の書式がある。
  行は実額で入れる（`wage` だけ書き `index` は書かない → コグニは `*` の手入力工賃になる）
- **レバーレートの決め方**（指数は見積書に無いので、レートの側から決める）:
  1. **速報報告書の「工賃単価」があればそれが正**（ヴァンガード 8,360 円）。工場に聞けるなら聞く
  2. 無いときだけ技術料から逆算する。`python .claude/skills/pdf-to-neo/scripts/guess_labor_rate.py <技術料を並べる>`
     が、`技術料 = 指数(0.1 刻み) × レート` を丸め単位で全行満たすレートを総当たりで挙げる
     （アクア: 8160 3630 20860 1810 18140 910 → 9,070 円の 1 件だけ。指数 0.9/0.4/2.3/0.2/2.0/0.1）
  3. **候補が複数出たら決めない**。千円単位の技術料しか無い書式は絞れない
     （ヴァンガードの技術料からは 5,000 円と 10,000 円が出るが、実際は速報の 8,360 円）。
     その場合は速報・工場確認で決め、決め手を報告に書く
  4. 定額の費用行（コーティング・写真代・ショートパーツなど）は逆算に混ぜない。候補が出ないときは
     税込のまま渡していないかも疑う（10-4）
  - 行は実額で入れるので、レートは `Setting.wb_PriceBase`（見積結果画面の「基本単価」）にしか効かない
- 部位の見出し行（金額の無い「左 クオータパネル修理」等）は明細にしない

## 10-7. `manual: true` を使ってよい場面（2026-09-09 アクアの失敗）

- `manual` は **ADDATA にその品目が無いとき**だけの逃げ道。使うと部品コード・標準品番・標準価格・
  部位ブロックが入らない NEO になり、コグニで開いても「工場見積を書き写しただけ」の状態になる
- **手入力にしてよい理由にならないもの**: 見積書に品番の印字が無い / 指数の印字が無い /
  工場書式が独自 / 部位の見出しが無い。**これらは全部、名称照合で解決する**
- アクア（ディーラー BP センター（トヨタ系）・品番も指数も印字なし・全 47 行）でこれをやってしまった。実測はこうだった:
  1. `manual` を全部外すと **46 行が名称照合で決まり、1 行（CPC ガラスコート部分施工）だけ未一致**
  2. `inspect_estimate.py` の ★ を見直し、**3 行を手入力に戻した**
     （左Rrドアヒンジボルト・左Rrドアロワヒンジボルト = 12.DB にドアヒンジのボルトが無い、
     左Frドアパネル脱し塗装 = 塗装側の作業でドアパネル本体と ref が重複する）
  3. ボデーロツカモールディングスクリユ 2 行は近似一致が別部位だったので `code: "2656"` を明示した
  4. 結果 **47 行中 43 行に部品コード**（手入力は CPC + 上の 3 行 = 4 行）。金額は変わらない
- **部品価格が ADDATA の標準価格と 1 円まで一致**したことが照合の裏付けになった
  （クリップ 9 個 810 円 = 標準 90 円 × 9、リヤドアパネル 41,100 円 = 標準 41,100 円 など）。
  純正定価で出す工場なら、照合が正しければ `*`（価格手入力）はほとんど付かない
- **手順**: まず `manual` なしで `inspect_estimate.py` にかけ、★（名称近似・複数候補）を 12.DB 名称一覧と
  照らして直す → 未一致の行だけ `manual: true` に戻し、理由を `comment` に書く
- `run_case.py` は、汎用車種でない案件で照合率が半分未満だと ★ で警告する

## 10-9. 標準価格の一致で照合と車両を検算する（2026-09-10 に確立）

- 純正定価で出す工場（ディーラー・トヨタ系）なら、**ref が正しければ見積の部品金額は ADDATA の標準価格と一致する**。
  `run_case.py` が「標準価格との一致 N/M 行」を出す。実測の目安は 96〜100%
- **ref の取り違えを見つける**: 2026-09-10 のヴァンガードは 64% で、内訳を見ると
  リヤドアパネル 75,500 円がフロントの ref（標準 70,700）、リヤドアアウトサイドモール 4,050 円が
  フロントの ref（標準 5,300）、リヤバンパリテーナ 3,710 円 ×2 がフロントの ref（標準 2,440）に付いていた。
  **見積書の RL 欄と部位見出しを名称に残す**（`左Rrドアパネル` のように書く）と解消する
- **車両（グレード）を絞る**: グレードが決まらない案件は、候補グレードごとに生成して一致数を比べる。
  アクア（型式指定・類別が資料に無い）は Ｂ 33/36・Ｘ 34/36・Ｇ 36/36・Ｚ 36/36 となり、Ｂ と Ｘ を除外できた
- **1,000 円未満の小物は対象外**。クリップ・グロメットは工場と ADDATA で価格が普通に食い違い、
  取り違えても損害が小さい。`run_case.py` は 1,000 円以上の行だけで ★ を出す
- **価格差だけでは断定しない。納品の可否にも使わない**。純正の価格改定・色別価格・工場独自価格で
  正当に食い違うことが実案件で確かめられている（C-HR のディスクホイール 65,600 円 ×2、
  N-ONE の Fr バンパフェイス 50,700 円、手入力の実験ケースのヘッドライト 45,000 円）。
  ★ が出たら ref と車両を一度確かめる、という**合図**として使う

### 10-9-1. 名称近似 × 価格不一致 = 取り違えの疑いが濃い行

- `run_case.py` の「要確認: 名称の近似で決めた行のうち標準価格も合わないもの」。
  **片方だけなら普通に起きる**（近似でも正しい / 純正の価格改定で価格だけ違う）が、両方そろうと疑わしい。
  実案件 10 件・約 500 行で 4 行しか出ない絞り込み
- **潰し方**: `scripts/find_ref_by_price.py <車種コード> <名称の一部> --unit <1個あたりの税抜単価>` で
  標準単価が一致する ref を探し、`code` に書く。部位で絞るときは `--block`
  （例: ヴァンガードの「クリップ 6 個 660 円」→ 単価 110 → `0971` に決まった）
- **候補が出ないとき**は ADDATA にその部品が無い（`manual: true` にして理由を書く）。
  例: ヴァンガードの「スクリューグロメット」は Y62 に該当名称が無かった
- 同名候補が多くて単価も合わないときは無理に当てず `manual` にする（当てずっぽうの ref より正直）

### 10-9-3. グレードが決まらない案件を部品金額で絞る

- 型式指定番号・類別区分番号が資料に無いと確度は `low` になり、候補の先頭が仮採用される。
  `run_case.py` が ★ で知らせる
- `python .claude/skills/pdf-to-neo/scripts/pick_grade.py <estimate.json>` が候補ごとに生成し、
  標準価格の一致数を並べる。**正しいグレードなら一致数が最大**になる。
  候補は「車種・年式・ボディ・グレード・エンジン」の組で数える（名前や記号が同じでも中身が違う候補があるため）
  （アクア: Ｂ 33/36・Ｘ 34/36・ＧＲ SPORT 34/36・Ｇ 36/36・Ｚ 36/36 → Ｂ・Ｘ・GR を除外）
- **同点が残るのが普通**。外装部品はグレードで変わらないことが多いので、金額だけでは 1 つに決まらない。
  そのときは車検証・ディーラーの型式表記（`MXPK11-AHXGB` の 4 文字目）・装備（ホイールキャップの有無など）で決め、
  決め手を報告に書く。決めたら `hints.grade_name` に書いて確定させる
  （同じ名前の候補が複数あって名前では決まらないときは `hints.candidate` に
  `{car_code, year_code, body_code, grade_code, fva_code}` を書く。書いた欄だけで固定される）
- 候補が 12 件を超える車は一覧が切られる。`pick_grade.py` が「※ 候補は全部で N 件」と出すので、
  そのときは型式指定・類別を資料から探して確度を上げるほうが早い

### 10-12. 塗装の「塗装面積」はコグニの「パネル面積」ではない（2026-09-10）

  「塗装面積」を別の列に持つ。reading の塗装行に面積を書いても paint.panels の area には入れない（20.DB の値が正）
- 工場のコグニと ADDATA の版が違うと、同じパネルでも標準指数が食い違う（ハイエース: 工場 3.2 / こちら 3.0）。
  **工賃は見積書の値をそのまま入れて手入力 `*` で保持する**。合計は合い、指数だけが実機と違う旨を報告に書く

### 10-13. ボデーシーリングは塗装の専用項目（2026-09-10）

- 塗装明細の「ボデーシーリング 10.00m」は `paint.sealing{m}`。draft が名称で振り分ける。
  ここを取りこぼすと **塗装工賃計が不足し、材料代（塗装工賃計 × 割合）も連動して狂う**

### 10-14. 協定額に合わせる（区分: 協定）

手順（**ここが正本**。SKILL.md と reading_schema.md はこれを参照する）:

1. **まず工場見積そのままの reading で検算を通す**。読み取りミスと協定調整を分けて確かめるため、ここを飛ばさない
2. 損害区分決定の指示に「◯◯の工賃で調整」とあれば、**その行の指数を 0.1 刻みで動かして寄せる**（工賃 = 指数 × レバーレート）。
   `index` と `wage` の両方を新しい値に直す
3. **小計も協定後の値に直す** —— ページ小計 `pages["N"]`（または `pages/page_N.json` の `subtotal`）と
   ブロック小計 `blocks[].subtotal` の**両方**（`reading_check.py` はどちらも行合計と突き合わせる）。印字の値は `note` に残す
4. 残る端数は `target_total`（税込）を reading に書き、**塗装材料代**で吸収させる（draft が計算して手入力 `*` で入れる）
5. 動かした前後の値と理由（損保の指示）を報告に書く
- 例（ハイエース 2026-09-10）: 工場見積 894,014 → 協定 885,500。
  課税小計の差 7,740 を クオータパネル取替 10.0→9.2（97,000→89,240、−7,760）で寄せ、
  残り +20 円を塗装材料代 50,440→50,460 で合わせた

### 10-17. 塗装パネルの面積は車のボディで決まる（2026-09-11）

塗装パネルマスタ（車種別 20.DB）は、**同じパネルコードをボディごとに別レコード**で持つ。面積が違えば
塗装指数も違うので、ボディを見ずに先頭の行を使うと工場のコグニと食い違う。

- レコードの 6 バイト目が **ボディコード**（0 = 全ボディ共通 / 10 / 20 …。KA81 の id と同じ 1 バイト整数）
- 選ぶ順: **そのボディ専用の行 → 全ボディ共通の行 → 同じコードの先頭**
- 車によっては **同じパネルがボディごとに別コード（枝番）**になっている。
  例: W90 ハイエースの L クオータパネルは 4800（ボディ 10・面積 150）と 4801（ボディ 20・面積 236）。
  明細の部品コードは 4800 だが、ボディ 20 の塗装パネルは 4801。同じパネル名のときだけ枝番へ進む
- **枝番の行き先が 1 コードに定まらないときは進まない**。同じ名前・同じボディでも面積が違う組があるため
  （**20.DB を持つ 1,204 車種を全走査して集計。2026-09-12**）:
  - **枝番でコードが違い、面積も違う組: 20 組（13 車種）** —— `panel()` が「行き先が複数」として控える。
    例 J81/J93/J94/J98 ﾃ-ﾙｹﾞ-ﾄ 4300（166 d㎡）と 4303（76 d㎡）、M11 LRﾌｴﾝﾀﾞ 4800（72）と 4802（0）
  - **同じコードが複数行あって面積が違う組: 258 組** —— こちらのほうが多い。
    例 C39 ﾌ-ﾄﾞ 0600 が 131 と 149、C48 LRﾄﾞｱ 2700 が 67 と 80。
    **2026-09-12 まで黙って先頭が選ばれ、警告も出ていなかった**（同日に控えるよう直した）。
  そのときは `inspect_estimate` が ★ で「ボディ NN 用の行を選べなかった」と出すので、
  **見積書に印字された dm² と突き合わせる**。違っていれば `paint.panels[].index` に見積書の指数を書く

**枝番パネルは「パネル追加」で書く —— 連動（`AddedFrom=0`）にしてはいけない**（2026-09-11 コグニ実機で確認）: 枝番へ進んだパネル（明細 4800 ｸｵ-ﾀﾊﾟﾈﾙ → ボディ 20 の塗装パネル 4801）は、明細の部品コードと塗装パネルのコードがずれる。これを「W/S 連動」（`AddedFrom=0`・工賃印 `''`）にすると、**コグニは塗装ページを開いたときに連動行を明細から作り直すので、明細に 4801 が無い 4801 の行は消える**。W90 ハイエース TRH229（ボディ 20）の実機で確かめた結果:

| 4801 の書き方 | コグニで塗装ページを開いた結果 | 塗装計 |
|---|---|---|
| `AddedFrom=1`・工賃印 `*`（パネル追加） | 2700 と 4801 の 2 行が残る | **176,560**（工場見積と一致） |
| `AddedFrom=0`・工賃印 `''`（W/S 連動） | 4801 が消え、枚数 1 で再計算される | 142,610（33,950 不足） |

生成器は枝番パネルを「パネル追加」のまま書く（`estimate_to_neo.py` の `linked_codes` は明細の部品コードそのままで突き合わせる。一時期入れた枝番補正 `_with_branch` は上の実測で取り消した。同名の関数を再び足さないこと —— `unit_consistency.test_paint_panel_branch_code_is_added_not_linked` が見張っている）。

**塗装パネルの `AddedFrom` の決め方**（実機 NEO で例外なし。本数・行数の実測値は HANDOFF §5-1 を正とし `tests/unit_handoff.py` が見張る）:

| 明細（ERParts）に | `AddedFrom` | 工賃印 |
|---|---|---|
| **同じ部品コードかつ同じ修理方法**の行がある | 0（W/S 連動） | `''` |
| 無い | 1（パネル追加） | `*` |

- 部品コードだけでなく**修理方法（取替 / 修理 / 板金）まで一致**していること。実機の連動パネルはすべてそうなっている（食い違い 0。2026-09-12 に W90 を足して数え直し）
- **指数が標準と違うこと（手入力）は `AddedFrom` と無関係**。手入力は `Manual=1` / 工賃印 `#` で表す。これを連動の理由にすると、明細に無いパネルが連動扱いになって消える
- 生成器は違反を `ValueError` で止める（`estimate_to_neo.py` の `_linked_ng`）

**2026-09-12 に人がコグニで W90 を最初から手入力して確かめた**（実機 NEO は NEO_check/_eva_exp/cogni_W90.neo、記録は `experiments/2026-09-12_W90_実機手入力.md`）:
明細 2700 取替 + 4800 取替 で塗装ページを開くと **自動連動するのは 2700 だけ**。クオータパネルは出ず、
パネル追加の一覧には 4801 だけがある（4800 は無い）。人は 4801 をパネル追加で足す → `AddedFrom=1`・`*`。
つまり生成器の書き方は人の手順そのもの。あわせて次も実機で確定した:

- `PaintingLinkParts` には **この車のボディに載っている（ボディ一致か共通の）20.DB 行がある部品だけ**が出る。
  4800 はボディ 10 専用行しか無いので出ない（生成器は `panel_for_body` で同じにした）
- 4800 取替の**標準指数は無し**（Time -1）。15.DB の J3/Q4 はホスト 4600 の下に「共通行 sub=4800」と
  「ボディ 20 行 sub=4801」があり、明細に 4801 が無いのでボディ 20 行は不成立。**共通行へは逃げない**
  （生成器は共通行を拾って 8.1 = 785,700 円を作っていた → 直した）。ただし 2700 のように
  ボディ行が**装備の不一致**で外れる場合は共通行 1.9 が採られる。sub 不一致とグレード/装備不一致で扱いが違う
- 標準が無くても `WorkCode` には 11.DB の区分レター（'J3Q4'）が入る（実機 25 本でも 47 行）
- パネル追加が 1 枚でもあると `PaintingPlan.BaseWageByManual='*'`（値は標準のまま）
- FVA が 'Z' 始まり（4WD）の車は `CarEVA` に Z を書かない（装備一覧に４ＷＤは出ない）

**塗装パネルのコードは枝番まで見て選ぶ**（面積＝塗装指数がボディで違うため）。連動にしてよいのは、明細の部品コードと塗装パネルのコードが**同じ**ときだけ。

実例（ハイエース 2026-09-11）: 修正前は 2700 面積 178 指数 3.0 / 4800 面積 150 指数 3.3 だったが、
ボディ 20 で選び直して **2700 面積 196 指数 3.2 / 4801 面積 236 指数 4.4** となり、工場見積の印字と一致した。

### 10-19. 材料代割合の既定は SHOUCHIKU ガイドライン表の「6500〜」列（2026-09-12、実案件 NEO 4,933 本）

見積書に材料代も割合も無いとき（`paint.material` も `paint.material_rate` も無い）の割合は、
SHOUCHIKU 見積ガイドラインの「塗装材料代割合」表の **6500〜 列**（表でオレンジ枠の列）の値を使う。
亮平さんがコグニで作った NEO 4,933 本の **83%** がこの列の値だった（工賃単価の帯には合わせていない。単価帯の列と一致は 27 本だけ）。

- 表は 塗料（2K / 水性）× クリヤー（標準 / 耐擦傷性 / スクラッチシールド）× 塗膜（ソリッド / メタリック / 2P / 3P）。
  コグニの高機能塗装 しない = 標準、耐スリ傷 = 耐擦傷性、スクラッチ = スクラッチシールド。フッ素と速乾は表に無いのでコグニ既定
- 値はコグニ既定（例 2K・2コートパールで 15%）よりかなり高い。具体的な値は git 外の表を見る（社内の参考値なので文書にも書かない）
- 表は社内の参考値なので git に入れない（`<NEO_CHECK_ROOT>/_reference/shouchiku_guideline.json`）。無い PC はコグニ既定になる
- 見積書に材料代や割合が印字されていれば、もちろんそちらを写す（この規則は既定値だけ）
- 同じ表にレバーレートの参考値もあるが、実案件 NEO で単価表の値と一致するのは 25% だけ。単価は見積書から逆算する（従来どおり）

### 10-20. 20.DB に無い塗装の部位は「手入力の塗装行」、工程は「追加項目」（2026-09-13、実案件 NEO 354 本・631 行）

見積書の塗装行で、20.DB のパネルに対応付けできないものは 2 種類ある。人はコグニで次のように入れている。

| 種類 | 例 | コグニの入れ方 | estimate.json | 材料代 |
|---|---|---|---|---|
| 部位（パネル）の名前 | ルーフサイド・リヤボデーフロア・テールゲート・ゲートパネル | 外板パネル画面の「行追加」（PaintingPanel.DisposalCode 9） | `paint.panels[]` に `{"manual": true, "name", "index" か "wage"}` | 対象 |
| 工程の名前 | アンダーコート・内板調色・チッピング・ヒンジ・レールカバー・フューエルリッド・ホースメント・ホイルハウス | 追加項目（PaintingOther） | `paint.other[]` | 対象外 |

- 手入力の塗装行は 部品コード空・面積と標準欄 -1・AddedFrom 1・SortNo 15。指数を入れた行は 工賃 = 指数 × 単価・印 `#`（Manual 1）、工賃だけの行は 指数 -1・印 `*`（Manual 2）
- 部品コードのあるパネルの後ろに入力順で並ぶ。塗装工賃計と材料代の対象に入るが、**加算基礎の枚数（単体塗/複数塗の判定も）には数えない**（60/60・16/16）。
  手入力の塗装行を足しただけでは加算基礎に `*` は付かない（241/245）
- 手入力の塗装行だけの見積は、加算基礎の標準が無い（BaseTimeStandard -1）。見積書に加算基礎があれば手入力 `#` で書く。バンパ加算基礎も付かない
- `draft_estimate.py` は、対応付けできない塗装行のうち工程の名前（上の表）を `paint.other`、それ以外で指数か工賃のある行を手入力の塗装行にする。
  ただし **20.DB のパネルに 1 行も対応付けできなかった見積は、全部を手入力にせず従来どおり一括計上**（名前の書き方がコグニと違う書式の疑いが強い）
- 工程なのに手入力の塗装行になった（またはその逆）ときは、`_draft_notes` を見て reading の name を直すか、estimate.json で `manual` / `other` を入れ替える

### 10-18. 修理(2) の塗装パネルは「1/2」で自動連動する（2026-09-12 実機 W66）

明細に 修理(2) を入れただけ（工賃・指数は未入力）で塗装ページを開くと、コグニは 20.DB にあるパネルを
**塗装面積 1/2** で自動連動する。1 枚でも 5 枚でも同じ（W66 シエンタ 0600 フード 81・2300 LF ドア 88・
4600 ロワバック 40・4802 L クオータ 68・5800 ルーフ 287 → すべて 1/2。実機 NEO `cogni_W66x` / `cogni_W66y`）。

- 指数は CHM の 1/2 列。複数枚だと 1 枚のときより小さくなる（4802 は 1 枚で 2.2、5 枚で 1.8 = 連動減算）。
  加算基礎数値も枚数で変わる（1 枚 2.8 → 5 枚 3.2）。生成器はどちらも一致
- `PaintingLinkParts` には修理行が全部載り（`PaintingFlag 0`）、`PaintingPanel.AddedFrom = 0`
- 下処理面積 `PrepareArea` は近似式（切上(面積 × 割合) × 0.345 四捨五入）が 4 枚で合い、**ルーフ 287 だけ 50 ≠ 実機 48**（J87 のルーフ 285 は式どおり。車種差か T_KEI_4 の係数と推定、未解決・金額に影響なし）
- 明細の修理行（工賃未入力）: `Time -1` / `WorkCode` 10 スペース / `ChangeTotal` は標準部品代 + 取替標準工賃 /
  `PartsPriceFlag 1`（標準品番が '-' で標準価格 0 でも 1）/ `ConstructGroup` は 11.DB の修理(S) 行のもの
  （4802 は 'Z0'、4600 は取替行が 'M8' でも修理行の '  '）
- **CHM に 1/2・1/3 の列が無いパネル（ロッカパネルアウタ 2602/3402、サイドシル 2601 など）は 1/1 固定**。修理で連動しても '1/1'・指数は 1/1 列（W66 2602: 25 dm²・1.3、下処理面積 9。`cogni_W66z`）。
  生成器は 1/2・1/3 を指定されても 1/1 で書き、注記を出す（実機で開けば 1/1 に戻るため）
- 工場見積が「修理 1/1」「1/3」と印字していればもちろんそれを書く（この規則は割合が読めない `auto_panels` の既定値）
- **パネルが無くバンパだけ塗る**見積は `panels: []` + `bumper_front`/`bumper_rear`。コグニは加算基礎数値を出さず（-1）、
  代わりに **バンパ加算基礎**（COM/BAN.DB 車形 × 塗膜クラス。W66 2コートパール 0.5）を `PaintingPlan.BumperBase*` に入れ、バンパ計に足す
  （W66 0010 新品 2.0 + 加算 0.5 = 2.5、`cogni_W66w` 全列一致）。バンパ部品の明細行が暫定指数 `$` なら塗装の工賃印も `$`（1 例からの推定）

### 10-16. 雛形 NEO と ADDATA の置き場（2026-09-11 に実測）

**雛形 NEO**（`claude_neo_pipeline/reference/template.neo`）

- 生成器は雛形を **器（テーブル定義と付随ファイル）としてしか使わない**。明細・車両・金額・顧客はすべて書き直す
- 実測: 実案件の NEO（明細 54 行・ハイエース・885,500 円）を雛形にして別案件（ランクル・21 行・1,576,432 円）を
  生成し、標準の雛形で作ったものと**全テーブル + AnSMB.txt + Ex.db + AnNote.ini を比べて差 0 件**。
  前の案件の情報は 1 つも残らない
- 差し替えたいときは環境変数 `NEO_TEMPLATE` にパスを置く（`template_path` 引数でも可）。
  解決順: 引数 → `NEO_TEMPLATE` → `reference/template.neo` → `reference/template_04011103.neo` → `サンプル見積PDF/04011103.neo`
- **入れ替える意味があるのは、コグニのバージョンが上がって表の定義そのものが変わったとき**だけ。
  そのときは「コグニで新規見積を作って保存しただけの、顧客情報の無い NEO」を置く

**ADDATA の場所**

- **自動検出**（`skill_env.find_addata()`）。この PC では 0.1 秒で `C:\Addata`（データ版 2026/08）を選ぶ
- ADDATA と認める条件: `COM` に `AnVer.DB` か `COM.CAB` があり、メーカー別フォルダ（1 文字）が 5 つ以上、
  そのうち 1 つ以上に `<car>01.DB` がある。**zip や圧縮ファイルではなくフォルダのまま**置く
- 探す順: コグニ本体の隣 → 固定ドライブの `Addata` / `ADDATA` / `Audatex\Addata` / 2 階層まで →
  割り当て済みネットワークドライブの同じ 3 か所。見つかった中から**データ版（`COM\AnVer.DB` の Number）が新しいもの**を選ぶ
- 見つからないときだけ 4 階層目・`Addata*` という名前まで広げる（上限 20 秒。`ADDATA_SCAN_SECONDS` で変えられる）
- 固定したいときは `env_check.py --addata "<パス>" --save`。`%USERPROFILE%\.claude\pdf-to-neo.local.json` に残る

### 10-15. 塗装が「一式」の見積書を、パネル別の明細に組み直す（2026-09-10）

工場見積が「塗装費用 ◯◯円」の一式しか出していない案件は、そのままだと NEO も
「塗装費用(工場見積)」1 行の一括計上になり、コグニで作った見積と見た目が変わる。
**コグニは部品を入れて塗装ページを開いた時点で 20.DB にあるパネルを自動計上し、加算基礎数値も入れる**ので、
同じ形に組み直せる。

- reading の paint に **`"auto_panels": true`** と工場の一式 `"total": <税抜>` を書く
  （`paint` / `coat` / `hf` も忘れずに。塗料・塗膜で指数が変わる）
- draft が **明細の 取替・板金・修理 行のうち 20.DB にあるパネル**を起こす（脱着は塗らない。
  面積 9999 のバンパは 23.DB 側なので `paint.bumper_*` で扱う）。取替 → 塗装「取替」、板金・修理 → 塗装「修理 **1/2**」
  （コグニの自動連動は修理パネルを 1/2 で起こす。実機 2026-09-12 W66 の 0600/2300/4600/4802/5800 修理 5 枚すべて 1/2。10-18）
- 工賃は**標準（CHM）に任せる**。加算基礎数値も枚数から標準で入る
- 工場の一式との差は **材料代**で埋める（`material` を手入力 `*` で入れ、`material_rate` も実態の割合にする）。
  合計欄の内訳（塗装工賃計・材料代）もこの配分に直す。**工場の一式（塗装費用計）と合計は動かない**
- **材料代が塗装工賃の 10〜90% に収まらないときは組み直さない**（明細に塗装対象の部品が足りない case。
  たとえば雹害のデントリペアのように塗装は全面なのに部品行が数枚しか無い案件）。★ の注記が出るので一括計上のままにする
- **数量 2 以上の塗装対象行があるときは自動で起こさない**（一括計上に戻して注記を出す）。コグニは左右を別コードで持つので、数量 2 の行は塗装パネル 2 枚になる。1 枚にすると塗装工賃が過少になり、その差が材料代に紛れてしまう。**左右は 1 行ずつに分けてから**もう一度かける
- **同じ塗装パネルに複数の明細行が行き着いたときは 1 枚にまとめ、取替行があれば「取替」で起こす**。枝番でコードの変わる車（明細 4800 → ボディ 20 の塗装パネル 4801）では、別コードの明細が同じパネルに行き着く（判断規則 10-17）。まとめないと同じパネルを 2 枚計上して塗装工賃が二重になる
- 例（ランクル 2026-09-10）: 一式 106,400 → フード 1 枚 32,000（指数 3.2）＋ 加算基礎 40,000（指数 4.0）
  ＝ 塗装工賃計 72,000、材料代 34,400（47.8%）。塗装費用計 106,400 と合計 1,576,432 は変わらない

### 10-11. 費用の名称は見積書の印字どおり（全角なら全角）で写す（2026-09-10）

- コグニの費用欄は 1〜8 が既定行（文字書き費用・内張り費用・配線費用・**ショートパーツ**・レッカー代・写真代他…）、
  9〜36 が自由記入。生成器は名称のキーワード（`estimate_to_neo.py` の `KEYMAP`）で既定行に寄せる
- **実機の形**（2026-09-10 に cogni_R2 / CXA で確認）: 既定行 1〜8 の名前は**全角の固定名**（'ショートパーツ' '写真代他'）で、
  自由行 9〜36 に入る名前は**半角カナ**（'ｺｰﾃｨﾝｸﾞ' 'ｴｰﾐﾝｸﾞ費用' 'ﾚｯｶｰ'）。draft は費用名を半角カナに直してから渡すので、
  自由行に落ちたときの見え方は実機と同じになる
- `reading.json` には **印字どおり**（全角なら全角）で写す。明細の部品名は ADDATA に合わせて半角カナでよいが、費用名は別
- **既定行に載るかは語による**（draft が半角カナに直すのは**カナだけ**で、漢字・英字はそのまま）:
  - **漢字・英字のキーワードはそのまま一致する** —— 文字書き・内張・配線・写真・診断・光軸・再設定・清掃・防錆・DTC
  - **カナのキーワードは `KEYMAP` に半角形がある語だけ一致する** —— ショートパーツ・アライメント・エーミング・コーティング（一致する）／
    レッカー・スキャン・リセット・ソナー（半角形が無い。名前に漢字のキーワードが混じっていなければ**自由行に落ちる**。金額・合計は同じ）
  - 既定行に載せたい費用があるときは、生成後に `Expense` の行番号か実機の費用画面で確かめる

  実測（2026-09-10。reading に書いた名前 → コグニの行）:

  | reading の費用名 | 行 | コグニ側の名前 |
  |---|---|---|
  | 文字書き費用 / 内張り費用 / 配線費用 / 写真代 | 1 / 2 / 3 / 7 | 文字書き費用 / 内張り費用 / 配線・配管費用 / 写真代他 |
  | ショートパーツ | 4 | ショートパーツ |
  | 室内清掃費 / アライメント調整費 / コーティング / エーミング費用 | 9 / 10 / 12 / 13 | そのまま（半角カナ） |
  | 光軸調整 / 防錆処理 / スキャン診断 | 18 / 24 / 26 | 電子機器点検再設定 / 防錆処理 / ｽｷｬﾝ診断 |
  | レッカー代 / ソナー点検調整費 | 36 / 35 | 自由行（ﾚｯｶｰ代 / ｿﾅｰ点検調整費） |
- 生成器側で表記ゆれを一般に吸収してはいけない。実機は半角カナの費用名を既定行へ寄せず自由行に置く
  （cogni_CXA の 'ﾚｯｶｰ' は自由行 36。ここを吸収すると全ファイル一致が崩れる）

### 10-10. 脱着・板金行の名称に左右が入っているか（2026-09-10）

- コグニは品番の出ない行（脱着・板金・修理）でも名称を 11.DB から作るので、**左右のある部品なら「左Fr…」が入る**。
  12.DB の名称は左右を持たないため、ここを取り違えると見積書で左右が分からなくなる
- 生成器は自動でこれを行う（可能作業に取替 K がある品目に限る）。**報告前に脱着行の名称に左右が入っているか目視する**
- 取替できない作業項目（「Fﾗｲｾﾝｽﾌﾟﾚｰﾄ(修理)」「Fｻｽﾍﾟﾝｼﾖﾝ(片側)」など）は 12.DB の名称のままが正しい。左右は付かない
- `run_case.py` の前後・左右の関門は、この修正で脱着行にも効くようになった（以前は照合先が左右を持たず素通りしていた）

### 10-9-2. 前後・左右の食い違い（これは言い訳が効かない誤り）

- 見積の名称と照合先（ADDATA 標準名称）で **前後（Fr/Rr）や左右（L/R）が食い違ったら ref の取り違え**。
  `run_case.py` が ★ を出し、`make_neo.py` は納品しない
- 実案件 10 件で誤検知ゼロ。ヴァンガードの取り違え 7 行だけを拾った
- **防ぎ方**: 見積書の RL 欄と部位見出しを名称に残す（`左Rrドアパネル`）。
  ADDATA に対応が無い部品（リヤのブラックアウトテープ 2 本目など）は `manual: true` にして理由を書く

## 10-8. 案件フォルダに既存の NEO があるとき

- 立会で作った NEO が既にあれば **`tests/neo_diff.py` で全列を突き合わせる**（既存ファイルは開くだけ。上書き禁止）。
  部品計・工賃計・塗装計が合っているかが一目で分かり、名称・作業区分の入れ方も学べる
- 差が出ても、実機 25 本（`_eva_exp/cogni_*.neo`）と食い違わない限り生成側を直さない。
  手入力行の標準名称・ConstructGroup は入力経路によって実機でも揺れる

## 11. やらないこと

- 見積書の数字を「正しい値」に直す（指数・材料代・工賃）
- 装備を根拠なく付ける
- `allow_unmatched` で照合漏れを許す
- 既存 NEO を上書きする、案件フォルダのファイルを消す
- 顧客情報を Codex・外部に送る、リポジトリにコミットする
