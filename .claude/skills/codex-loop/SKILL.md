# codex-loop — 反復的な敵対的バグハント

## これは何のためか

一度のレビューで見つかるバグは、その回に選んだ観点の範囲に限られる。
観点を変えて何周も回すと、前の周では見えなかった欠陥が出てくる。
このスキルは、その反復を「毎回ちがう観点を選ぶ」「確定したものだけ数える」
「自分の修正も疑う」という3つの規律で運用するための手順書。

大事なのは **確定バグだけを積み上げる** こと。推測を混ぜると、
存在しない問題を追って時間を溶かし、本物の問題が埋もれる。

## 1周のかたち

```
観点を1つ選ぶ → 敵対的レビュアーに調べさせる → 確定バグを修正する
→ 自分の修正を次の周のレビュー対象に含める → 確定バグが0になるまで繰り返す
```

### 観点を1つ選ぶ

毎周、**まだ調べていない観点**を1つだけ選ぶ。widely でなく deeply に掘るため。
観点の例（対象によって読み替える）:

- 入力の解析（境界・異表記・壊れた入力）
- 生成物の中身（実際に開いて、元データと突き合わせる）
- 状態管理と同時実行（利用者間の分離、キャッシュ、一時ファイル）
- エラー処理（利用者が詰む経路、内部エラーの露出）
- 実際の操作手順（戻る・やり直す・差し替える）
- 数値の正しさ（丸め、符号、単位、税)
- デプロイ環境との差（本番のOS・言語版・権限・ディスク）
- **直前のコミットが入れた回帰**（これは毎周入れる。下記参照）

調べ終えた観点は記録しておき、レビュアーに「ここはもう潰した」と伝える。
伝えないと同じ場所を掘り返して周が無駄になる。

### 敵対的レビュアーに調べさせる

サブエージェントを使えるなら、観点ごとに1体ずつ立てる。独立した目で見せるのが
狙いなので、自分の見立ては渡さない。渡すのは次の3つ。

1. **対象と背景** — 何をするコードか、どのコミットを見るか
2. **今回の観点**と、**もう潰した観点**（掘り返し防止）
3. **実行環境** — アプリの起動方法、生成物の開き方、テスト用の道具、
   使えない資源（APIキーが無い等）を正直に

そして必ずこう指示する:

> **実際に実行して確認した確定バグだけを報告してください。**
> 各件について 1.症状 2.再現手順と実行出力 3.原因(file:line) 4.影響 5.修正案。
> 確定バグがゼロなら「確定バグなし」と明記してください。
> 推測での水増しは有害です。

「実行出力を貼らせる」のが要。これが無いと、コードを読んだだけの推測が
バグとして報告され、直す価値のないものに手を入れることになる。

### 確定バグを修正する

報告をそのまま信じない。まず自分で再現してから直す。
再現できないものは、レビュアーの誤りかもしれないので保留にして次へ回す。

### 自分の修正を疑う

**これが一番大事**。修正は新しいバグを生む。実際、この手順を運用すると
「前の周の自分の修正が原因」という報告が繰り返し出てくる。
だから次の周のレビュー対象には、必ず**直前のコミットの差分**を含める。

具体的には、次の周のレビュアーにこう頼む:

> `git show <直前のコミット>` を読み、**私の修正が壊したもの**を探してください。

## 止めどき

**新しい確定バグが0だった周が来たら止める。** それ以外では止めない。
「もう十分だろう」で止めると、たいてい残っている。

## 修正を確定させる前にやること

直した瞬間にコミットしない。次を通してから。

1. **回帰テストを育てる** — 確定バグは1件ずつテストに落とす。
   同じバグが二度出ないようにするのと、後の周で自分が壊したときに気づくため。
2. **生成物を開いて突き合わせる** — 帳票やバイナリを作るコードでは、
   コードを読むだけでは足りない。実際に生成し、中身を元データと照合する。
3. **利用者の操作で通す** — 画面があるならブラウザで通しで動かす。
   関数単位で正しくても、画面の状態管理で壊れていることがある。
4. **変えていない経路が変わっていないことを確かめる** — 生成物を
   バイト単位で比較できるなら比較する。「触っていないつもり」が
   一番あてにならない。

## 報告の書き方

利用者に返すときは、確定した事実と、確認できていないことを分けて書く。

- 症状は**利用者から見た言葉**で書く（「合計が3.16倍になる」）
- 影響は**数字**で示す（「¥165,000 → ¥388,487」）
- 自分の修正が原因なら、そう書く。隠すと同じことを繰り返す
- 検証できなかったことは、できなかったと書く
  （実データが無い、本番に接続できない、等）

## よくある落とし穴

- **1周で終わらせる** — 観点を変えればまだ出る。0になるまで回す
- **推測を混ぜる** — 「かもしれない」は確定バグではない。数えない
- **自分の修正を信じる** — 修正は最も疑うべき変更
- **同じ観点を掘り返す** — 潰した観点をレビュアーに伝える
- **コードを読んで満足する** — 生成物を開く。画面を操作する
- **止めどきを気分で決める** — 0の周が来るまで止めない
